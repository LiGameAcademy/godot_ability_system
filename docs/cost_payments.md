# 费用准备与提交

`CostFeature` 现在按运行时 Vital 实例汇总内置 `VitalCost`。
同一个魔力槽有两笔 10 点费用，就需要 20 点；只有 15 点时，查询和支付都失败，余额不变。
同时消耗魔力、生命等不同 Vital 时，也先检查全部条件，再写入全部余额，最后通知变化。
查询保持只读；实际支付会重新准备计划，不能沿用前摇开始时的余额。

配置 Resource 和传入的 context 不保存付款计划。同一份费用可以被两个角色共享，
每次调用都解析当前角色的 Vital。数组里重复放入同一个费用 Resource，仍按两笔费用计算。
同一 Vital 在一次批量付款里只发送一次变化通知；UI 不应依赖“每笔费用一个信号”。
通知参数是这次付款的数值快照；通知回调随后可以改变余额，读取实时余额请调用组件 API。

## 透支和非法配置

不允许透支的费用先保留足额余额。剩余余额为正时，允许透支的费用可以把它扣到零。
例如 15 魔力同时支付普通费用 4 和透支费用 20，结果为零，与配置数组的排列顺序无关。
若只有 4 魔力，普通费用占满余额，透支费用就不能支付，整批余额不变。
零费用可以在零余额时支付，不发无变化的通知。

负数、NaN、无穷金额、空费用 Resource、缺失 Vital 和类型错误的 context 会失败。
`skip_cost` 和空费用数组仍跳过支付。不要直接改写 Vital 当前值制造超出上限的状态。

## 自定义费用的兼容范围

数组只有一个旧自定义 `AbilityCostBase` 时，仍调用它的检查和支付钩子。
继承 `VitalCost` 并重写钩子的业务类，也按自定义费用处理，不能绕过钩子直接扣款。
单项旧钩子自身可能先修改外部数据再返回失败；插件无法替它回滚，这部分保证仍由业务实现承担。

多项费用中，只要有一个旧自定义钩子，仍会在付款前拒绝并发出提示。
要与其他费用、非零冷却一起提交，需要采用下面的准备契约。
继承 VitalCost 的业务类也要显式选择契约；不能靠继承关系绕过自定义规则。

## 自定义库存、充能费用

费用 Resource 保存数量等配置，重写 `supports_prepared_payment()` 返回 true，
并实现 `prepare_payment(ability_comp, instigator, pending) -> AbilityCostPayment`。
准备只构建本次运行计划，不改余额、占用库存、发信号或缓存到配置 Resource；不能 await。
`pending` 是本次已准备计划的数组副本，计划对象仍可用于合并费用。
找不到运行数据或配置非法时返回 null，整批失败，不会退回旧支付钩子。

每份计划实现三步：

1. `can_apply() -> bool` 只读检查当前余额、金额和目标有效性。准备结束及写入前都会复核。
2. `apply() -> void` 同步写入已复核的数据，必须无失败、无通知、无外部回调，也不能再次触发付款。
3. `notify_changes() -> void` 在所有费用、冷却和提交记录写好后通知外部。可使用本次扣款快照；发通知前检查目标是否仍有效。

同一库存被多项费用引用时，在 pending 中找到该库存对应的计划，累加金额，返回同一个计划；
批次会去重，只写入、通知一次。不能让两份各自检查余额的计划分别扣同一个库存。
不同自定义费用类型若共用余额，也必须协调同一计划；内置 Vital 余额请用 VitalCost，
不要另写自定义计划再扣同一个 Vital，否则双方无法汇总。这些是扩展实现的责任，不由插件推断外部数据的含义。

完整可运行的库存示例见 [issue_19_custom.gd](../tests/cases/issue_19_custom.gd) 中的
InventoryCost / InventoryPayment：两笔各 2 件的费用合计需要 4 件；只有 3 件时整批不扣，
有 5 件时剩 1 件，同一配置可供两个角色共享。该示例是无 UI 回归用例，不要求采用特定背包组件。

直接调用采用新契约的 `AbilityCostBase.try_pay()` 也走准备、复核、写入、通知。
抽象的旧 `_try_pay()` 仍需实现以保留旧类兼容；新契约启用后不会调用它，可返回 false。
`_can_pay()` 仍负责单项只读资格检查；组合资格由 CostFeature 汇总计划检查，不能只逐项调用 can_pay。

本契约适用于同线程的本地状态；同步复核后到全部写入结束之间没有信号、回调或 await。
插件不会捕获自定义脚本错误并假装支付成功，也不会替不遵守契约的实现回滚。
网络请求、数据库付款、发通知后才知道成败的操作不能放到 apply 中；需要业务自己的事务或预约协议。

## 技能提交入口与阶段

`GameplayAbilityInstance.try_commit()` 读取当前执行的 context；传入字典时在副本上覆盖本次参数。
默认一次提交费用和冷却，内置 Vital 或采用准备契约的自定义费用复核失败时冷却也不变。
费用、冷却和提交记录全部写好后，才发送技能数据、Vital 与自定义付款通知。
如果要保留分阶段流程，可传入 `pay_cost`、`start_cooldown`，或使用旧的单项提交节点。
默认 CostFeature/CooldownFeature 缺失表示免费或无冷却；写错自定义 Feature 名称会失败。

主动模板在前摇后用 `AbilityNodeCommit` 一起提交；标准名称的显式 Feature 配置同样生效。
连击仍在开始时扣费、结束时进冷却；开关仍在开启时扣费、关闭时进冷却。
连击段中的统一节点关闭其冷却请求，调整的是段树副本，原资源不变。
`skip_cost` 跳过这次费用；`skip_cooldown` 沿用原来只跳过资格检查的含义，关闭开关时仍提交冷却。

旧的 `AbilityNodeCommitCost`、`AbilityNodeCommitCooldown` 适配同一入口。
提交记录按技能实例和本轮执行保存，重置 BT 不清掉记录；成功后的重复提交不再扣费或重启冷却。
下一轮成功激活时建立新记录，结束和取消后仍能读取 `get_commit_state()` 的副本。
记录列出已完成的费用/冷却阶段（含免费或跳过），不代表具体扣款额，也不是完整技能结果。

提交前取消，不扣款、不进冷却；提交后的取消不自动退款，也不撤销冷却。
提交通知中取消或退出角色时，收尾等通知结束后执行，防止半提交状态被新一轮施法复用。
这里的提交成功只说明付款阶段已经完成，不表示技能一定命中或执行成功。

旧自定义树若把两个单项节点放在不同阶段，本次不会把它们自动挪到一起。
需要同时成功的相邻节点请换成 `AbilityNodeCommit`，否则仍保留分阶段结果，后续失败不自动回滚前一阶段。
单项旧自定义费用可以单独提交；与非零冷却组合提交会在调用支付钩子前拒绝，需要迁移到准备契约。

`CostFeature.try_pay(ability, context)` 接入本轮提交记录；传入 null 时仍是独立付款，每次调用会再次支付。
直接 `VitalCost.try_pay()`、周期性的 `AbilityNodeApplyCost` 保留原入口；周期扣费不会变成一次性费用。
`CooldownFeature.start_cooldown()` 保留直接设置计时器的用途，需要提交幂等时应调用统一入口或提交节点。

## 迁移与范围

CostFeature.prepare_payment 的返回类型从 VitalCostBatch 改为 CostPaymentBatch，
调用方通常只需继续使用 apply / notify_changes / try_pay；不要再直接访问 Vital 专用 payments 字典。
VitalCostBatch 和 GameplayVital.try_pay_batch 保留原用途。
未提供自动退款、跨网络事务或完整技能结果；已提交后的撤销需要业务明确制定补偿规则。

资格查询后余额变化、角色隔离、透支、非法金额、小数精度和自定义钩子边界。

单次写入/通知、提交通知中取消、目标退出和共享配置的 A/B 隔离。
